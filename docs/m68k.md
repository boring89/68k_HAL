# 68k 虛擬機（emu/m68k + Musashi）

這份文件說明 68k_HAL 怎麼在 x86 上執行 68k 程式。M3 由自動排程一次做完，使用者還沒有逐步確認過，所以這裡盡量寫清楚「是什麼、為什麼這樣做」。

## 1. 它在解決什麼問題

Classic Mac OS 的程式是為 Motorola 68000 系列 CPU 寫的，x86 CPU 看不懂它們的機器碼。要執行它們，需要一個**模擬器**：用 C 寫一個「假的 68k CPU」，一條一條讀取 68k 的指令，用 x86 的程式碼完成同樣的效果。

比喻：x86 是只會說英文的人，68k 程式是一份法文食譜。模擬器是個即時口譯員：每次讀一句法文（一條指令），翻成英文動作（C 程式碼）再做出來。

模擬器自己維護 68k 的「世界」：

```
  68k CPU 狀態（Musashi 的全域變數）        guest RAM（一塊 byte 陣列）
  ┌───────────────────────────┐            ┌──────────────────────┐
  │ D0..D7   資料暫存器       │            │ 0x00000000 向量表    │
  │ A0..A7   位址暫存器 (A7=SP)│  讀/寫     │ 0x00001000 程式      │
  │ PC       程式計數器       │ ────────►  │ ...                  │
  │ SR       狀態暫存器 (CCR) │            │ 0x00008000 堆疊頂    │
  └───────────────────────────┘            └──────────────────────┘
```

**CCR（Condition Code Register）**是 SR 的低 5 位元：X（延伸）、N（負數）、Z（零）、V（溢位）、C（進位）。算術指令會更新它們，分支指令（BEQ、BNE…）根據它們決定要不要跳。

## 2. 為什麼用 Musashi

原本 `emu/m68k` 是自己寫的玩具（MOVE 與 ADDI 寫死）。完整的 68k 有上千種指令/定址模式組合，還有例外、特權模式、各代 CPU 的差異，自己寫要很久也很容易錯。Musashi（Karl Stenerud，MIT 授權，MAME 長期使用）是成熟的 C 實作，支援 68000 到 68040。MIT 授權與本專案的 GPL-3.0 相容。

決定與理由（M3_PLAN.md 的設計決定）：

| 項目 | 決定 |
|---|---|
| CPU 目標 | 68030（Mac II 以後的主力；SingleStepTests 只有 68000，驗證時切 68000 模式） |
| Musashi 原始碼 | `third_party/musashi/`，**完全不修改**；來源與 commit 在 `VERSION`，授權在 `LICENSE` |
| 我們的程式 | `emu/m68k/`：`vm`（封裝）、`trap`（A-line）、`m68kconf.h`（設定） |
| 單一 VM | Musashi 的 CPU 狀態是全域變數，所以同時只能有一個 VM |

## 3. 一條指令怎麼被執行

Musashi 的建置有個特別的步驟：`m68kmake`（Musashi 附的小程式）讀取 `m68k_in.c` 裡的指令表，**產生** `m68kops.c`——1967 個指令處理函式。Makefile 在 `build/` 底下做這件事，產生的檔案不進 git。

```
m68k_in.c ──m68kmake──► m68kops.c（1967 個 handler）
                              │
 m68k_execute(cycles) 的迴圈：
   ┌─► ① hook(pc)              我們的 m68k_vm_instr_hook（見第 5 節）
   │   ② 讀 16 位元 opcode      → m68k_read_memory_16（我們的 vm.c）
   │   ③ jump_table[opcode]()   → 對應的 handler 改暫存器/記憶體
   │   ④ 扣掉這條指令的 cycles
   └── cycles 還有剩 → 回到 ①
```

**cycle** 是 CPU 時脈週期，Musashi 用它估計每條指令花多久；`m68k_vm_run(n)` 最多跑 n 個 cycles（至少一條指令），或遇到 STOP 就提早結束。

### 封裝層 API（`emu/m68k/vm.h`）

| 函式 | 用途 |
|---|---|
| `m68k_vm_init(ram, size, cpu)` | 接上 guest RAM，選 68000 或 68030 |
| `m68k_vm_load(addr, data, len)` | 把程式放進 guest RAM |
| `m68k_vm_reset(entry, sp)` | 寫入向量表（位址 0 = 初始 SP，4 = 初始 PC）並重置 CPU |
| `m68k_vm_run(cycles)` / `m68k_vm_halted()` | 執行；程式執行 STOP 即視為結束 |
| `m68k_vm_get_reg` / `set_reg` | 讀寫 D0-D7、A0-A7、PC、SR、USP、ISP |
| `m68k_vm_read8/16/32`、`write8/16/32` | 直接存取 guest RAM（大端序） |
| `m68k_vm_set_write_watch` | 每寫一個 byte 就通知（測試用） |

68k 是**大端序**（高位 byte 在低位址），x86 是小端序。`vm.c` 的記憶體 callback 逐 byte 組合，所以 guest RAM 裡的資料保持 68k 的樣子。超出 RAM 範圍的讀回 0、寫入忽略。

## 4. 記憶體對應

```
 host（x86 kernel）                          guest（68k）
 虛擬位址 0x10000000 ─┐                       位址 0x00000000
   ...                │  同一塊 4 MiB         ...
 虛擬位址 0x103FFFFF ─┘                       位址 0x003FFFFF
```

- **host 測試**：guest RAM 只是一個一般的 `uint8_t` 陣列。
- **kernel**：`kernel/m68k/guest.c` 向 PMM 要 1024 個連續 frame（4 KiB × 1024 = 4 MiB），用 `hal_mmu_map` 逐頁映射到虛擬位址 `0x10000000`，再把這個位址交給 `m68k_vm_init`。第一次使用時才分配，之後重複使用（只清零）。
- 為什麼要映射到固定虛擬位址：kernel 的程式透過虛擬位址存取記憶體，PMM 只給實體 frame；映射後 guest RAM 在 kernel 眼中就是一塊連續的記憶體，不論實體 frame 在哪。

層次關係：`emu/` 只依賴 `kernel/lib/`（與 Musashi），不知道 HAL、PMM 或分頁；把 RAM 準備好是 `kernel/` 的責任（見 `docs/hal.md` 第 2 節的規則，`tools/check_boundary.sh` 檢查）。

## 5. A-line trap 的原理

Classic Mac OS 的程式不是直接呼叫函式來使用系統服務（Toolbox 與 OS），而是執行一條**特殊的非法指令**：opcode 最高 4 位元是 `1010`（`$Axxx`），稱為 A-line。

```
  程式碼：  ...  MOVE.L ...
                 $A9F4        ← "我要呼叫 trap 0x9F4"（例如 ExitToShell）
                 MOVE.L ...
```

真正的 68k 遇到 A-line 會觸發例外（向量 10），由系統的例外處理程式查表找到對應的服務。我們用另一個辦法：Musashi 在每條指令執行前會呼叫 hook（`M68K_INSTRUCTION_HOOK`，在 `m68kconf.h` 開啟）。`vm.c` 的 hook 檢查：

```
opcode & 0xF000 == 0xA000 ?
   是 → PC 跳過這 2 個 byte
        → m68k_trap_dispatch(opcode, pc)：記錄到 log，呼叫登記的 handler
        → 再檢查新的 PC（可能又是 trap，或是 STOP）
   否 → 讓 Musashi 正常執行
```

`emu/m68k/trap.c` 的資料：

| 資料 | 說明 |
|---|---|
| handler 表 | 4096 項（trap 編號 = opcode 低 12 位元），`m68k_trap_set_handler` 登記，預設沒有 handler |
| log | 最近 32 筆（opcode、位址），`m68k_trap_total` 是總數 |

目前沒有任何 handler：trap 只被記錄然後略過。**這是之後 M4（Toolbox）的接口**：handler 可以讀寫暫存器（`m68k_vm_get_reg`/`set_reg`）與 guest 記憶體，實作 Toolbox 呼叫。handler 執行時 PC 已經指向 trap 之後，想改變流程就改 PC。

連續 trap 最多處理 65536 次（`MAX_TRAP_CHAIN`），避免 handler 一直把 PC 設回 trap 造成當機；超過就讓 Musashi 走正常的 line-A 例外。

## 7. SingleStepTests 結果

SingleStepTests/680x0 是公開的 CPU 測資：每個測試給定「執行前」的完整 CPU 與記憶體狀態，執行**一條指令**，並給出「執行後」的狀態。這些狀態是用一個通過所有其他測試集的實作產生的。

我們用的是 68000 的 `v1` 資料夾（124 個檔，每個約 8000 個測試，共 1,000,058 個）。下載後放在 `tests/data/sst/*.json.gz`（已加入 `.gitignore`），來源 repo commit `e0d5ece9670205cc84a0101081837deb446f86a3`。

```bash
make test-sst     # 約 1 分鐘；每個檔印出一行
```

流程：`tools/sst_convert.py`（Python，只做 JSON 解析，不執行測資）把 JSON 轉成文字行，由 `tests/host/sst_run.c` 讀入，設定暫存器與記憶體，用 `m68k_vm_run(1)` 執行一條指令，比較暫存器（D0-D7、A0-A6、USP、SSP、SR、PC）與測資列出的記憶體；也檢查 Musashi 有沒有寫到測資沒提到的位元組。**不比較**：cycle 數、bus 交易、prefetch queue 內容。

結果：

| | 通過 / 總數 |
|---|---|
| 全部 | 807,145 / 1,000,058（80.7%） |
| 排除「預期發生 address error」的測試 | 807,145 / 821,971（**98.2%**） |

**Address error 的測試（178,087 個）Musashi 全部與參考結果不同**。這是設計上的差異，不是 bug：

- 真正的 68000 有 prefetch queue（預先讀 2 個字的指令佇列），跳到奇數位址的 PC 在**同一條指令內**就會發現並觸發 address error。Musashi 沒有 prefetch queue，直到下一次取指令才發現，所以單步測試時還沒發生。
- address error 的 stack frame 裡，status word 的未使用高位元在硬體由 opcode 填入，Musashi 填 0。

其餘沒有 100% 的指令（以「非 address error」測試計）：

| 指令 | 通過 / 總數 | 原因（依失敗案例的旗標判斷，未逐一查證） |
|---|---|---|
| ABCD | 7251 / 8065 | BCD 運算的 N、V 旗標在手冊中是「未定義」，Musashi 與參考實作的選擇不同 |
| SBCD | 4350 / 8065 | 同上（另有少數結果位元組不同） |
| NBCD | 4655 / 8065 | 同上 |
| ASR.b | 6423 / 8065 | 旗標差異（失敗案例是 V/C 旗標） |
| ASR.w | 6079 / 7142 | 同上 |
| ASR.l | 7034 / 8065 | 同上 |
| DIVS | 3092 / 4992 | 溢位時 N、V 旗標（手冊中為未定義） |
| DIVU | 3715 / 4964 | 同上 |
| ASL.b | 8063 / 8065 | 2 個個案 |

這些我們只記錄，不修改 Musashi。Classic Mac OS 的程式不應依賴「未定義」的旗標行為。

## 8. 已知限制

- **FPU**：guest 被當作「沒有 FPU 的 68030」。Musashi 無法關閉 FPU 模擬（`m68kcpu.c` 直接 include `m68kfpu.c`，需要 softfloat；kernel 的 `freestanding/libc.c` 仍保留 `m68k_vm_fatal` 出口以便連結），所以 `m68k_vm_instr_hook` 在每條指令執行前檢查：opcode 的高 4 位元是 `0xF`（F-line）就不交給 Musashi，改由 `raise_line_f` 手動做 line 1111 例外（vector 11，位址 `VBR + 0x2C`）：把 SR、出錯指令的 PC、format/vector 字（format 0）推到 supervisor stack，再跳到 handler。這與 A-line trap 同一個迴圈處理，所以 handler 的第一條指令也是 F-line 時仍然正確（上限 65536 次，防止無窮迴圈）。測試：`tests/m68k/fline.s`（host）與 `test_m68k_guest_fline_exception`（QEMU）。Classic Mac OS 偵測 FPU 的方式就是看 F-line 例外，所以這樣的行為與「沒有安裝 68881」的 Mac 一致。
- **address error 不補檢查**：Musashi 沒有 prefetch queue，所以 SingleStepTests 中「預期 address error」的案例時序不同（見第 7 節）。我們選擇不補：目標是 68030，它允許未對齊的資料存取（不會有 address error），只有奇數 PC 取指令才會，而正常的 Mac 程式不會這樣做。
- **CI 不跑 SST**：測資約數百 MB 需自行下載，所以 `make test-sst` 不在 `make test` 與 CI 中，修改 `emu/m68k` 後請手動執行。
- **kernel 的 libc 替身**：`emu/m68k/freestanding/include/` 有 `assert.h`、`setjmp.h`、`limits.h`、`math.h`、`stdio.h`、`stdlib.h` 的最小版本，只在建置 Musashi 時用 `-isystem` 加入。`setjmp` 用 GCC 的 `__builtin_setjmp`（Musashi 用它在 address/bus error 時跳出指令）。kernel 沒有連 libgcc，所以 `divdi3.c` 自己提供 64 位元除法（`DIVU.L` 的 64 位元被除數會用到）。
- **CPU 狀態是全域的**：同時只能有一個 VM；一個 kernel 只有一份 guest RAM（4 MiB，固定位址）。
- **沒有 MMU**：關閉了 PMMU 模擬（`M68K_EMULATE_PMMU 0`）與 68040。Mac OS 7 的 32 位元定址不需要它。
- **沒有中斷與 trace**：`M68K_EMULATE_TRACE`、中斷 acknowledge callback 都沒開。
- **kernel 版 Musashi 用 `-O2`**（其他程式碼沒有 `-O`），因為 CPU 核心在 `-O0` 下很慢；Musashi 本身以 `-w` 編譯（它的寫法不符合我們的警告設定）。
- **示範與 selftest 都只執行我們自己寫的小程式**；專案不包含任何 Apple ROM 或系統軟體。
