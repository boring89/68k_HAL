# x86-64（64 位元）移植

`arch/x86_64/`、`platform/pc/boot/boot64.asm`、`linker64.ld`、Makefile 的 `ARCH=x86_64`

目標：kernel 能使用 P520 的 64 GB 記憶體與 4 GiB 以上的裝置位址（xHCI、HDA 的 BAR 在 `0x43ffff…`）。
**64 位元現在是預設**（`make` → `build/`）；32 位元用 `make ARCH=i386`，輸出到 `build/i386/`，CI 兩個都測。
（P8 由自動排程一次做完，**使用者尚未審核**；修改前請先帶使用者過一遍這份文件。）

## 0. 摘要

| 項目 | 做法 |
|---|---|
| 為什麼 | 32 位元 kernel 只看得到 4 GiB 以下：P520 的 64 GB RAM 用不到，xHCI／HDA 的 BAR 在 4 GiB 以上（實機回報）也碰不到 |
| 開機 | GRUB（Multiboot 1／2）→ 32 位元進入程式 `boot64.asm`：建開機頁表、PAE、`EFER.LME`＋`NXE`、開分頁、載入 64 位元 GDT → 跳到 64 位元 C |
| 位址空間 | 低半邊 = 使用者；高半邊 = kernel（見 1 節的圖） |
| 使用者程式 | **仍是 i386 靜態 Linux 程式**，在 compatibility mode 執行（和 Linux 的 ia32 相容層同樣的做法），所以 musl SDK、Lua、TinyCC、SQLite、dash、make、Kilo、box 都不用重編；64 位元使用者程式（`syscall`、x86-64 ABI）還沒做 |
| 其他 CPU | 只在保護模式遞增計數後 `hlt`（沒有 per-CPU 資料，所以不進長模式） |
| 測試 | `make test`（64 位元）與 `make ARCH=i386 test` 跑同一組測試；`test-uefi`、`test-usb-image`、`test-power`、Mac 的 `test-rom-qemu`（畫面 CRC 與 host 相同）都在 64 位元通過 |

## 1. 位址空間

```
0x0000000000000000 ┌──────────────────────────┐
                   │ 使用者程式（i386，4 GiB 以下）│  每個行程一份 PML4 的低半邊
0x0000800000000000 ├── (non-canonical 空洞) ──┤
0xFFFF800000000000 ├──────────────────────────┤  HHDM：所有 RAM 的直接映射（2 MiB 頁）
                   │ HHDM（PML4 項目 256）      │  hal_phys_to_virt(p) = p + 0xFFFF800000000000
0xFFFFC00000000000 ├──────────────────────────┤  PML4 項目 384
                   │ heap                       │  0xFFFFC00000000000 起（HEAP_VIRT_BASE）
                   │ m68k guest RAM             │  0xFFFFC00040000000
                   │ vmap 視窗（MMIO、BAR）     │  0xFFFFC00080000000 起，任何實體位址都可映射
0xFFFFFFFF80000000 ├──────────────────────────┤  PML4 項目 511：kernel 映像（-mcmodel=kernel）
                   │ .text .rodata .data .bss   │  .text 可執行，其餘 NX
                   └──────────────────────────┘
```

- 開機頁表（`boot64.asm`）把前 4 GiB 映射三次：identity（進入程式還在實體位址跑）、HHDM、kernel 映像；進入 C 之後 `paging_init` 重建正式的頁表：HHDM 只映射 RAM（可用記憶體、ACPI reclaimable、開機資料），用 2 MiB 頁；kernel 映像用 4 KiB 頁，`.text` 之外全部 NX。
- **kernel 半邊的 PML4 項目（256、384、511）開機時建好，之後每個新位址空間都複製這幾項**，所以 kernel 的任何位址在每個行程裡都有效；低半邊（0–255）是行程私有。
- 因為 HHDM 涵蓋所有 RAM，kernel 可以用 `hal_phys_to_virt()` 直接存取任何頁表、任何 frame，不需要 32 位元版的「遞迴映射」或「視窗」；`space.c` 因此簡單很多。
- 使用者頁（`HAL_MMU_USER`）不設 NX（沿用「可讀即可執行」，CLAUDE.md 的已知問題）。

## 2. 開機流程

1. GRUB 以 Multiboot 載入 kernel：`objcopy -O elf32-i386` 把 64 位元 ELF 轉成 32 位元 ELF（GRUB 的 `multiboot` 與 QEMU 的 `-kernel` 都只吃 32 位元 ELF），位址欄位是實體位址（映像放在 1 MiB）。
2. `boot64.asm`（32 位元）：檢查 CPUID 的長模式位元 → 建開機頁表（PML4 → PDPT → 2 MiB 頁，Intel SDM Vol.3A 4.5、OSDev "Setting Up Long Mode"）→ CR4.PAE → `IA32_EFER.LME`（同時開 NXE）→ CR0.PG → `lgdt` → far jump 進 64 位元程式。
3. 64 位元程式設好堆疊，把 Multiboot 資訊的**實體位址**交給 C（`multiboot_info_phys()`），之後都經 `hal_phys_to_virt()` 讀。
4. 從這裡開始與 32 位元共用 `kernel/main.c`：GDT／IDT（64 位元版）、PMM、分頁（正式頁表）、heap、PCI……。

## 3. 64 位元專屬的部分（`arch/x86_64/`）

- `gdt/`：64 位元 GDT；16 位元組的 TSS（`rsp0` 與 IST：double fault、NMI 各有自己的堆疊）；**保留 32 位元 user code／data segment**（compatibility mode）。
- `interrupt/`：16 位元組的 IDT 閘；`isr.asm`／`irq_stub.asm` 手動 push 15 個暫存器；`interrupt_frame` 是 64 位元暫存器。
- `mmu/`：4 層分頁（`paging.c`）、`hal_mmu.c`（`hal_mmu_map` 等介面不變，位址是 `uintptr_t`；支援 `HAL_MMU_WRITE_COMBINING`）、`space.c`（每個行程一份 PML4，kernel 半邊共用）。
- `task/`：context switch 保存 rbx／rbp／r12–r15，`hal_context_t.sp` 是 64 位元；FPU 狀態照舊用 FXSAVE。
- `user/`：`iretq` 到 32 位元 user code segment（CS = compatibility mode），`int 0x80` 經 64 位元 IDT 進 kernel；系統呼叫的參數仍是 32 位元暫存器。
- `test/selftest_x86_64.c`：分頁、HHDM、4 GiB 以上的記憶體（QEMU 給 4.5 GiB，PMM、HHDM、vmap 都讀寫 4 GiB 以上的頁）、IA32_PAT。

## 4. 為什麼使用者程式用 compatibility mode

重編整個 userland（musl、Lua、TinyCC、SQLite……）成 x86-64 要有 x86_64 的 musl SDK、`syscall` 指令的入口、64 位元的 ELF 載入器，工作量大且與「kernel 能用 64 GB」這個目標無關。compatibility mode 讓 CPU 在長模式裡執行 32 位元程式：分頁與 kernel 是 64 位元的，使用者程式看到的是 4 GiB 的 32 位元位址空間。限制：每個行程最多 4 GiB（堆疊固定 2 MiB 等限制照舊）；`sysenter`／`syscall` 不用，仍是 `int 0x80`。

## 5. 移植時遇到的問題

| 問題 | 原因 | 解法 |
|---|---|---|
| 行程裡的 fbcon 在 64 位元 page fault | `pc_framebuffer_map` 用 identity map 映射螢幕，只存在於第一個位址空間 | 改成 `vmap`（kernel 視窗，所有位址空間共用）；`test-fb` 原本誤用 32 位元 kernel 所以沒抓到，已改成 `$(BUILD)/kernel-gfx.elf` |
| Multiboot 結構裡的位址 | 全是實體位址，64 位元 kernel 不能直接當指標 | 一律經 `hal_phys_to_virt()`；Multiboot2 轉出的表放進 kernel 映像，用實體位址（`image_phys()`）填進 32 位元欄位 |
| `-m64` 與 `-m32` 的 C 標準差異 | 本機 gcc 15 預設 `gnu23`（`bool` 是關鍵字），CI 的 gcc 13 預設 `gnu17` | kernel 的 CFLAGS 固定 `-std=gnu11`，沒 include `<stdbool.h>` 的檔案補上 |
| QEMU 的 `-kernel` | 只吃 32 位元的 Multiboot ELF | `objcopy -O elf32-i386`（見 2 節） |
| 其他 CPU（AP） | 沒有 per-CPU 資料，進長模式後沒地方放堆疊與狀態 | AP 只在保護模式遞增計數後 `hlt`（`trampoline64.asm`） |

## 6. 還沒做

- 其他處理器不進長模式、不排程（沒有 per-CPU 資料）。
- 64 位元使用者程式（`syscall`、x86-64 ABI、x86_64 的 musl SDK）。
- 使用者頁不設 NX。
- 32 位元建置是否保留由使用者決定（目前 `ARCH=i386` 保留並進 CI）。

## 7. 移植清單（S0）

以下是 S0 開始時的盤點，保留作為「哪些地方依賴位元數」的紀錄。


### 7.1 已經與位元數無關（用 `-m64` 編譯 kernel/、drivers/、emu/、platform/ 只有 4 個警告，已修）

- `kernel/` 的指標與位址一律用 `uintptr_t`；`hal/` 的介面（`hal_mmu_map(uintptr_t, uintptr_t, ...)`）、PMM 的 API 也是。
- PCI BAR 的解碼（`platform/pc/pci/pci_bar.c`）本來就支援 64 位元 BAR；只有 `hal_pci_map_bar` 與 `vmap` 擋掉 4 GiB 以上。
- Musashi 與 `emu/` 在 host 測試時就是 64 位元。

### 7.2 S0 已改的共用程式碼

| 位置 | 改了什麼 |
|---|---|
| `hal/mmu.h` | 新增 `hal_phys_to_virt()`：32 位元是 identity，64 位元（`-DHAL_PHYS_BASE`）加上 HHDM 的位移 |
| `platform/pc/boot/multiboot.c`、`hal_boot.c` | Multiboot 結構裡的位址都是實體位址，一律經 `hal_phys_to_virt` 讀；Multiboot2 轉出的表（在 kernel 映像裡）用實體位址 `image_phys()` 放進 32 位元欄位；新增 `multiboot_info_phys()` |
| `kernel/mac`、`kernel/user/process.c`、`kernel/block/ramdisk.c` | 開機 module 的內容用 `hal_phys_to_virt(module.base)` 取得指標，不再直接把實體位址轉成指標 |
| `kernel/memory/memory.c`、`arch/x86/interrupt/idt.c`、`kernel/user/process.c` | 指標轉 `uint32_t` 的地方先轉 `uintptr_t` |

### 7.3 必須為 64 位元重寫的部分（`arch/x86_64/`、`platform/pc/`）

| 區域 | 32 位元的假設 | 64 位元的做法 |
|---|---|---|
| 開機 `platform/pc/boot/boot.asm`、`linker.ld` | 保護模式進入點、kernel 放在 1 MiB、identity mapped | 32 位元進入程式：建立開機頁表、PAE、`EFER.LME`、開分頁、載入 64 位元 GDT、跳到 higher half |
| GDT/TSS `arch/x86/gdt` | 8 位元組描述元、32 位元 TSS（`esp0`） | 64 位元 GDT（含 16 位元組的 TSS：`rsp0`、IST）；保留 32 位元 user code segment（compatibility mode） |
| IDT 與例外 `arch/x86/interrupt` | 8 位元組閘、`pusha`、`interrupt_frame` 是 32 位元暫存器 | 16 位元組閘、手動 push 15 個暫存器、新的 `interrupt_frame` |
| 分頁 `arch/x86/mmu` | 2 層、4 MiB 一個 PDE、遞迴映射、`space.c` 用視窗編輯別的行程的目錄 | 4 層頁表，透過 HHDM 直接存取任何頁表；kernel 半邊（PML4 的 256–511）所有行程共用；低半邊是行程私有 |
| context switch `arch/x86/task` | 保存 edi/esi/ebx/ebp，`hal_context_t.sp` 是 `uint32_t` | 保存 rbx/rbp/r12–r15，`sp` 是 `uint64_t` |
| 使用者模式 `arch/x86/user` | `iret` 到 ring 3、`int 0x80` | 一樣用 `iretq` 到 32 位元 user code segment（compatibility mode），`int 0x80` 經 64 位元 IDT；i386 程式不用重編 |
| `arch/x86/cpu/cpu.h` | `cpu_read_cr*` 回傳 `uint32_t`、`pushfl` | 共用，改成 `uintptr_t`、`pushf` |
| AP 啟動 `platform/pc/smp/trampoline.asm` | 真實模式 → 保護模式後呼叫 C | 其他處理器只回報後 `hlt`（沒有 per-CPU 資料），所以在保護模式用組語遞增計數器後停住 |
| `platform/pc/vmap` | 視窗在 `0xE0000000`、拒絕 4 GiB 以上 | 視窗放在 kernel 半邊，BAR 可在任何實體位址 |
| `platform/pc/dma` | 實體位址 `uint32_t`、PMM 只有 4 GiB | DMA 記憶體仍然要求在 4 GiB 以下（`pmm_alloc_frames_below`） |
| PMM `kernel/memory/pmm.c` | bitmap 固定 4 GiB（128 KiB） | bitmap 涵蓋 128 GiB（4 MiB，在 .bss） |
| kernel 的位址常數 | `HEAP_VIRT_BASE 0x20000000`、`M68K_GUEST_RAM_BASE 0x10000000` 在低 4 GiB | 64 位元移到 kernel 半邊（低半邊整個留給使用者程式） |
| `platform/pc/hal_init.c` | `map_boot_data` identity map 開機資料 | 不需要：HHDM 涵蓋所有 RAM |
| `platform/pc/power` | `lidt` 的描述元 6 位元組 | 64 位元是 10 位元組 |
| 測試 `arch/x86/test/selftest_x86.c` | 分頁測試依賴遞迴映射與 identity map | 64 位元版另寫（`arch/x86_64/test/`） |
| Makefile | `-m32`、`nasm -f elf32`、`ld -m elf_i386`、`qemu-system-i386 -kernel` | `ARCH=x86_64`：`-m64 -mcmodel=kernel -mno-red-zone -mno-sse…`、`elf64`、`elf_x86_64`；QEMU 的 `-kernel` 只吃 32 位元 ELF（Multiboot 1），所以用 `objcopy -O elf32-i386` 轉換 |

### 7.4 不改

- 使用者程式（i386 靜態 Linux 程式）繼續跑，不重編（見計畫的設計決定）。
- Musashi（不可修改）：kernel 版用 `-m64` 另編，使用 `emu/m68k/freestanding/` 的替身 libc。
